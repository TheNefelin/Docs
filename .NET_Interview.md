```csharp
int numero = 10;         // Tipo fijo, compilación
var texto = "Hola";      // Inferido en compilación, no cambia
```


## 3. Ordenar números sin `.Sort()` (descendente)
```csharp
int[] numeros = { 5, 2, 9, 1, 7 };
for (int i = 0; i < numeros.Length - 1; i++)
{
    for (int j = 0; j < numeros.Length - 1 - i; j++)
    {
        if (numeros[j] < numeros[j + 1])
        {
            int temp = numeros[j];
            numeros[j] = numeros[j + 1];
            numeros[j + 1] = temp;
        }
    }
}
```

```csharp
}
```

## 7. Detección de Anagramas en una frase
- MARY WORKS IN ARMY
```csharp
public class AnagramFinder()
{
    public void EncontrarAnagrama(string frase)
    {
        string[] palabras = frase.Split(' ');
        Dictionary<string, List<string>> mapaAnagramas = new();

        foreach (string palabra in palabras)
        {
            string palabraOrdenada = OrdenarLetras(palabra);
           
            if (!mapaAnagramas.ContainsKey(palabraOrdenada))
                mapaAnagramas[palabraOrdenada] = new List<string>();

            mapaAnagramas[palabraOrdenada].Add(palabra);
        }

        foreach (var grp in mapaAnagramas)
            if (grp.Value.Count > 1)
                Console.WriteLine($"Anagramas encontrados: {string.Join(", ",grp.Value)}");
    }

    private string OrdenarLetras(string palabra)
    {
        return new string(palabra
            .ToLower()
            .OrderBy(c => c)
            .ToArray());
    }
}
```
```csharp
AnagramFinder anagramFinder = new AnagramFinder();
anagramFinder.EncontrarAnagrama("MARY WORKS IN ARMY");
```

## 8. Encontrar el Primer Numero Positivo
- { 1, 3, 6, 4, 1, 2 } resultado 5
```csharp
class Solution
{
    public int solution(int[] A)
    {
        HashSet<int> grp = new HashSet<int>();

        foreach (int n in A)
        {
            if (n > 0)
            {
                grp.Add(n);
            }
        }

        for (int i = 1; i <= A.Length + 1; i++)
        {
            if (!grp.Contains(i))
            {
                return i;
            }
        }

        return 1;
    }
}
```
```csharp
var solution = new Solution();
var res1 = solution.solution(new int[] { 1, 3, 6, 4, 1, 2 }); //5
var res2 = solution.solution(new int[] { 1, 2, 3 }); //4
var res3 = solution.solution(new int[] { -1, -3 }); //1
var res4 = solution.solution(new int[] { 2, 3, 7, 6, 8, -1, -10, 15 }); //1
var res5 = solution.solution(Enumerable.Range(1, 100000).ToArray()); //100001
```

# Programación Orientada a Objetos (POO)
## 1. Pilares de la POO
- Encapsulamiento: Oculta detalles internos. Acceso mediante propiedades (get/set).
- Herencia: Una clase puede heredar de otra: class Perro : Animal.
- Polimorfismo:
    - Sobrecarga: Mismo nombre, distintos parámetros.
    - Sobrescritura: Clase hija redefine métodos de la clase padre con override.
- Abstracción: Se expone solo lo esencial. Usando abstract o interface.

## 2. Ejercicio: Herencia y polimorfismo
```csharp
public class Animal
{
    public virtual void HacerSonido() { }
}

public class Perro : Animal
{
    public override void HacerSonido() => Console.WriteLine("Guau");
}

public class Gato : Animal
{
    public override void HacerSonido() => Console.WriteLine("Miau");
}
```
```csharp
List<Animal> animales = new List<Animal> { new Perro(), new Gato() };
foreach (var animal in animales) animal.HacerSonido();
```

## 4. Interface vs Clase Abstracta
| Característica        | Interface                      | Clase Abstracta               |
| --------------------- | ------------------------------ | ----------------------------- |
| Instanciable          | ❌ No                           | ❌ No                          |
| Implementación lógica | ✅ (desde C# 8.0) con `default` | ✅ Sí                          |
| Herencia múltiple     | ✅ Sí                           | ❌ No                          |
| Propósito             | Contrato                       | Base común con lógica parcial |

# APIs y Arquitectura Web
## 1. Principios fundamentales del diseño de una API REST
### Los principios clave del diseño REST (Representational State Transfer) son:
- **Uniformidad de la interfaz:** Todos los recursos se acceden mediante URLs claras y un conjunto fijo de métodos HTTP (GET, POST, PUT, DELETE). Esto permite que los clientes interactúen de manera predecible.

- **Separación cliente-servidor:** El cliente y el servidor se desarrollan y despliegan de forma independiente, lo que mejora la escalabilidad y la flexibilidad.

- **Sin estado (stateless):** Cada solicitud debe contener toda la información necesaria, lo que permite escalar horizontalmente sin mantener sesiones en el servidor.

- **Caché:** Las respuestas deben incluir información sobre si pueden ser almacenadas en caché, mejorando así el rendimiento.

- **Sistema en capas:** Una arquitectura REST puede estar compuesta por múltiples capas (como gateways, balanceadores, proxies), lo que facilita el mantenimiento y la evolución del sistema.

- **Código bajo demanda (opcional):** El servidor puede enviar código ejecutable al cliente, como scripts JavaScript.

#### ¿Cómo aseguran la escalabilidad y mantenibilidad?
- **Escalabilidad:** Al ser sin estado, las APIs REST pueden manejar múltiples solicitudes simultáneas distribuidas en diferentes servidores.

- **Mantenibilidad:** La interfaz uniforme y la separación de responsabilidades hacen que el código sea más fácil de mantener y evolucionar sin afectar a los clientes.

## 2. Inyección de Dependencias (DI) y Tiempo de vida Scoped, Transient y Singleton
- **La Inyección de Dependencias** (DI) es un patrón de diseño utilizado para implementar la Inversión de Control (IoC). Permite gestionar desde el contenedor de dependencias los servicios que una clase necesita, promoviendo un código más limpio y desacoplado.
```csharp
public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        // Registrar servicios
        services.AddScoped<IMyService, MyService>();
        services.AddTransient<IOtherService, OtherService>();
        services.AddSingleton<IThirdService, ThirdService>();
    }
}
```
| **Tiempo de vida** | **Creación de la instancia**                           | **Alcance**                                  | **Caso de uso**                                                                                       |
| ------------------ | ------------------------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Scoped**         | Se crea una vez por **solicitud HTTP**.                | Misma instancia durante toda la solicitud    | Servicios que deben compartir datos dentro de una misma solicitud, como `DbContext` en EF Core.       |
| **Transient**      | Se crea cada vez que se inyecta.                       | Instancia diferente cada vez.                | Servicios ligeros, sin estado y que no requieren compartir datos (por ejemplo, validaciones simples). |
| **Singleton**      | Se crea una sola vez durante la vida de la aplicación. | Misma instancia compartida entre solicitudes | Servicios globales, como loggers, proveedores de configuración o almacenamiento en caché.             |

> [!IMPORTANT]
>  **Nota:** Con Scoped, todas las operaciones dentro de una misma solicitud HTTP (como múltiples llamadas internas al servicio) usan la misma instancia. En cambio, Transient genera una nueva instancia para cada inyección, incluso dentro de la misma solicitud.

## 3. Diferencia entre `PUT` y `PATCH`: ¿cuándo usar cada uno?
| **Método HTTP** | **Descripción**                                                 | **Comportamiento**                                                            | **Cuándo usarlo**                                                                                  |
| --------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **PUT**         | Reemplaza **completamente** un recurso existente con uno nuevo. | Requiere enviar todos los datos del recurso, incluso si solo cambió un campo. | Cuando se desea sobrescribir el recurso completo.                                                  |
| **PATCH**       | Modifica **parcialmente** un recurso existente.                 | Solo requiere los campos que van a cambiar; el resto permanece intacto.       | Cuando se quiere actualizar parcialmente un recurso (por ejemplo, solo un campo como el "nombre"). |

Ejemplo:
- Supón que tienes un recurso de usuario:
```json
{
  "id": 1,
  "nombre": "Carlos",
  "email": "carlos@email.com"
}
```
- Un `PUT` para cambiar solo el correo debe enviar todo el objeto:
```json
PUT /usuarios/1
{
  "id": 1,
  "nombre": "Carlos",
  "email": "nuevo@email.com"
}
```
- Un `PATCH` puede enviar solo el campo modificado:
```json
PATCH /usuarios/1
{
  "email": "nuevo@email.com"
}
```

## 4. Diferencia entre Middleware, Action Filters y Delegating Handlers en .NET Core
| **Componente**          | **Descripción**                                                                                                            | **Etapa del ciclo de vida**               | **Casos de uso**                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Middleware**          | Componentes que se ejecutan en la **tubería de solicitudes HTTP** antes de llegar al controlador y después de salir de él. | Muy al inicio (nivel global)              | Logging, manejo de errores globales, autenticación, redirecciones, CORS, compresión, etc.         |
| **Action Filters**      | Filtros que se ejecutan **antes y/o después** de que se ejecuten los métodos del controlador (acciones).                   | A nivel de controlador o acción           | Validaciones, logging específico por acción, autorización adicional, modificación del resultado.  |
| **Delegating Handlers** | Parte del `HttpClient` pipeline, permite interceptar **peticiones salientes** hacia APIs externas.                         | En llamadas HTTP salientes (`HttpClient`) | Agregar cabeceras, políticas de reintento, logging, autenticación al consumir servicios externos. |

| Característica  | Middleware                 | Action Filters                       | Delegating Handlers                   |
| --------------- | -------------------------- | ------------------------------------ | ------------------------------------- |
| ¿Dónde se usa?  | En el servidor (pipeline)  | En los controladores/acciones        | En cliente HTTP (HttpClient)          |
| ¿Intercepta...? | Todas las peticiones HTTP  | Peticiones/respuestas de acciones    | Llamadas HTTP **salientes**           |
| ¿Cuándo usarlo? | Lógica global (logs, CORS) | Validación de inputs, auth en acción | Lógica de cliente HTTP (retry, token) |

## 5. Escalabilidad y Eficiencia en una Aplicación .NET de Alto Tráfico.
Diseñar una aplicación .NET que maneje millones de solicitudes diarias requiere tomar decisiones de arquitectura bien fundamentadas para garantizar tanto **escalabilidad** como **eficiencia de rendimiento**.

---

### ⚙️ 1. Elección de Arquitectura

#### a. Arquitectura basada en microservicios
- Divide la aplicación en servicios independientes que pueden escalarse y desplegarse de manera individual.
- Mejora el aislamiento de errores y permite escalar solo las partes críticas (por ejemplo, pagos, autenticación).

#### b. API Gateway
- Centraliza las solicitudes entrantes.
- Maneja autenticación, autorización, limitación de tasa (rate limiting), logging y routing.
- Ejemplo: Ocelot o YARP (Yet Another Reverse Proxy) en .NET.

#### c. Escalabilidad horizontal
- Desplegar múltiples instancias de servicios en contenedores o máquinas.
- Usa orquestadores como **Kubernetes** o **Azure App Services con autoscaling** para ajustar recursos dinámicamente.

#### d. Asincronía y mensajería
- Usa colas (RabbitMQ, Azure Service Bus) para desacoplar procesos intensivos (como el procesamiento de imágenes o notificaciones).
- Minimiza el tiempo de respuesta de las peticiones HTTP.

---

### 🧠 2. Estrategias de Caché

#### a. Caché en memoria
- Usa `MemoryCache` o `IMemoryCache` para datos que se consultan frecuentemente y cambian poco.
- Ideal para configuraciones, listas de catálogos, etc.

#### b. Caché distribuida
- Usa Redis o Memcached para compartir cache entre múltiples instancias de la app.
- Permite almacenar sesiones, tokens, respuestas frecuentes, etc.

#### c. Cacheado por capa
- **Cliente**: Controla caché con headers HTTP (`Cache-Control`, `ETag`).
- **CDN**: Distribuye contenido estático globalmente con servicios como Cloudflare o Azure Front Door.
- **Servidor**: Usa estrategias de invalidación para mantener la cache fresca.

---

### 🧱 3. Balanceo de Carga

#### a. Load Balancer (Balanceador de carga)
- Distribuye el tráfico entre múltiples instancias para evitar sobrecarga en una sola.
- Puede ser a nivel de aplicación (L7) o de red (L4).
- Ejemplos: Azure Load Balancer, NGINX, AWS ELB.

#### b. Health Checks y Failover
- Configura health checks para detectar instancias caídas.
- El balanceador evita enviar tráfico a instancias con fallos.

---

### 🔐 4. Optimización de rendimiento adicional

- Minimizar llamadas a base de datos: Usa EF Core con consultas optimizadas (`AsNoTracking`, `Include` inteligente).
- Compresión de respuestas: Middleware para GZIP reduce el tamaño de los datos enviados.
- Uso de `IAsyncEnumerable` y streaming para respuestas grandes en partes.
- Profiling y monitoreo: Usa Application Insights, Prometheus, o ELK para métricas y logs detallados.
